# 业务场景版检验 Prompt

## 设计原则

- **需求方只写：业务场景 + 需求。** 这就是一个普通工程师能写出来的东西。
- **不写**：hook 名称（`parallel`/`pipeline`/`phase`/`schema`）、阶段怎么划、起几个 agent、事件名、验收细则。
  这些是 DSH 内部实现和测试者的关注点，不该由需求方在 prompt 里雕花。
- **检验是观察者的事**：编排事实、事件链、画布核对，由跑完之后的人在外部核对，不占用需求方的 prompt。

---

## 一、用户侧 Prompt（只需复制这一块）

```text
我们需要一份"AI 代码审查工具"的选型评估报告，用来决定要不要引入、以及优先选哪一款。

背景：
- 团队现在纯靠人工 Code Review，效率低、标准不统一；
- 预算有限，希望工具能接入现有 CI 流程；
- 关注点：审查准确率与误报率、对现有语言和仓库的适配成本、定价、数据合规。

请你调研市面上的候选工具（具体选哪几款由你判断），最后给我一份 markdown 报告，包含：
1. 是否建议引入；
2. 若引入，优先选哪一款；
3. 各候选的横向对比和主要理由；
4. 主要风险与限制。

这件事子任务比较多，请用工作流（workflow）并行拆分来做，报告直接写到工作区。
```

就这么多。没有 hook、没有阶段、没有数量、没有事件名——因为需求方只需要说清楚"要什么"和"做到什么程度"。

### 可选补充

上面那句"请用工作流并行拆分来做"通常已经足够触发 `workflow` 工具。如果 Agent 仍然逐个手工调用子 agent，补一句纯业务语言即可：

```text
请务必用 workflow 工具把这次调研编排起来跑，而不是一个个单独调用。
```

## 二、验收清单（测试者/观察者用，不要写进 prompt）

跑完之后由测试者核对。记 **N** = 实际启动的 agent 数，**P** = 实际使用的阶段数（这两个值从实际事件里读，不预设）：

- [ ] `tool-workflow/run-start` 恰好 1 条、`run-end` 恰好 1 条，且 `stopReason = completed`。
- [ ] `tool-workflow/agent-start` 条数 == `agent-end` 条数 == N；每个 `seq` 一一配对。
- [ ] `workflow` 工具返回的 `agentsStarted` == N。
- [ ] 「工作流」标签页有 1 条运行记录；阶段列数 == P；子 Agent 卡片数 == N。
- [ ] 同一阶段的卡片同列纵向排列，不同阶段横向成列；编排 Agent 与子 Agent 之间有连线。
- [ ] 所有 `agent-end.outcome = completed` 时，卡片显示「已完成」，编排 Agent 也显示「已完成」。
- [ ] 产出报告的卡片能列出该文件，点击后可在右侧预览。
- [ ] 业务侧：报告文件存在，且给出了"是否引入 / 优先哪款 / 理由 / 风险"。

**判据**：不变量全部成立即通过。N 是几不重要——数量本来就是 Agent 按任务结构自己定的。

## 三、这套拆法的意义

| 谁 | 负责什么 | 会写什么 |
| --- | --- | --- |
| 需求方（工程师） | 业务目标、验收标准（业务层面） | "要一份选型报告，结论要有理由和风险" |
| DSH / Agent | 要不要用工作流、怎么拆阶段、起几个 agent | 由它自己决定，Harness 只兜底上限 |
| 测试者 / QA | 插件行为是否正确 | 事件链、卡片数、状态、文件预览 |

所以「检验 workflow 插件」这件事，**不需要需求方懂编排**：他正常提业务需求，测试者在旁边看画布和事件就够了。
