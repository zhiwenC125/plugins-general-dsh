# Revolution UI 架构 V1

> 状态：试探性产品设计基线。本文区分“仓库已实现能力”和“尚未联调的探索能力”，不得以视觉完整度代替实现状态。

## 1. 产品信息架构

Revolution 是一个本地优先、连接团队控制平面的工程工作台。一级导航建议固定为：

```text
个人
├── 收件箱                     # 飞书/会议/GitHub/Coding/远程工作包
├── 我的工作包                 # 个人承担、待接收、待移交
└── 会话                       # DSH session

团队
├── 项目与 Scrum
├── 开发看板
├── 契约与依赖
└── 审批中心

工程
├── 仓库
├── 资源中心
├── 执行中心
└── 工具与插件
```

左侧导航表达稳定领域；项目内的“总览 / 看板 / 流程 / 会话 / 产物”使用二级导航。个人与团队不是两套产品，而是同一工作包事实在不同权限和范围下的投影。

## 2. 看板与代码仓库

### 决策

**不自建 GitHub/Coding 式 Git 托管平台，也不把浏览器网页当成 Revolution 的主要仓库体验。**

采用混合接入：

- GitHub/Coding/GitLab 继续是代码、Issue、PR、CI 和 Release 的权威源。
- 本地 Git 负责工作区、分支、diff、commit 和可离线操作。
- Revolution 提供原生“仓库工作区”，聚合当前工作包真正需要的内容：仓库、分支、变更、PR、检查、Issue、产物和权限状态。
- 高级仓库管理通过“在 GitHub/Coding 中打开”深链或内置浏览器完成，V1 不重复实现组织设置、复杂 review、Actions 编辑器等成熟能力。
- 开发看板是 Revolution 的一等页面；外部 Issue 映射到工作包，但不得用外部看板覆盖工作包的责任、契约、审批和执行状态。

### 页面结构

```text
工作包标题 / 负责人 / 业务状态 / AI 执行状态
├── 看板：待澄清｜可开始｜进行中｜待评审｜完成
├── 仓库：本地状态｜分支｜diff｜PR｜CI
├── 会话：DSH 对话与工具执行
└── 产物：commit｜PR｜构建物｜测试｜审批证据
```

仓库卡必须显示权威来源和新鲜度，例如 `GitHub · 2 分钟前同步`、`本地工作区 · 未推送 2 commits`，避免把缓存投影误认为远程实时状态。

## 3. 资源中心

### 决策

资源中心使用**独立一级页面**，开发看板和工作包内只显示上下文资源卡与快捷入口。

原因：资源具有与任务不同的生命周期、权限、容量、调度和审计要求；把全部资源塞进开发看板会让任务流被库存管理淹没。但完全分离又会丢失“这个任务正在占用哪块板卡、哪个 token 配额”的上下文。

### 统一资源模型

| 类型 | 示例 | 关键状态 |
|---|---|---|
| 原子硬件 | STM32 板、JTAG、串口、摄像头 | 在线、占用、固件、校准、健康 |
| 台架与算力 | HIL 台架、GPU runner、编译 runner | 队列、租约、容量、地域 |
| 组合资源 | 机器人、机器狗、充电桩 | 子资源拓扑、整体健康、当前任务 |
| 软件能力 | MCP、工具链、SDK、License | 版本、兼容性、权限、到期 |
| 配额与凭据 | LLM token 池、API quota、云预算 | 余额、速率、作用域、有效期 |

凭据正文永远不在 UI 中展示；只展示 vault 引用、作用域、到期时间、消费和审批状态。

### 资源中心页面

```text
资源概览
├── 筛选：硬件｜组合设备｜台架/算力｜软件能力｜配额
├── 指标：可用 / 占用 / 故障 / 待审批 / 即将到期
├── 资源列表或拓扑
└── 详情侧栏
    ├── 当前状态与遥测
    ├── 组成与依赖
    ├── 当前租约/责任人
    ├── 使用历史
    ├── 关联工作包
    └── 申请、预约、释放、报障
```

工作包中的资源区只显示：已绑定资源、租约剩余时间、权限缺口和“前往资源中心”。

## 4. 工具与插件

### 决策

采用双轨模型：

1. **开发模式**：团队开发者从本地目录或受信仓库加载插件，用于调试；清楚标记“开发中 / 未签名”。
2. **市场模式**：普通用户从 Revolution 插件市场安装经签名、固定 digest、完成权限声明和兼容验证的发布版本。

插件市场可以连接 Git 仓库或 Release 作为来源，但禁止“任意 URL clone 后直接执行”。Registry 记录：owner、版本、digest、DSH/Revolution 兼容范围、权限、风险等级、SBOM、签名、撤销状态和发布说明。

### 页面结构

```text
工具与插件
├── 已安装
├── 团队目录
├── 市场
├── 更新
└── 开发模式

插件详情
├── 能力与适用工作包
├── 权限与数据出口
├── 版本/兼容性/来源
├── 安全与签名状态
└── 安装、升级、停用、卸载
```

安装前必须显示权限差异；新增危险权限的升级不能静默安装。

## 5. 责任变更与权限审批

责任变更是工作包详情中的一等操作，而不是编辑一个姓名：

```text
工作包详情 → “变更承担人”
├── 当前 accountableOwner / assignee / executor / approver
├── 候选承担人及能力/负载
├── 移交范围与未完成事项
├── 权限差异
│   ├── 将授予：仓库 write、板卡租约
│   └── 将回收：OTA staging
├── 临时或永久、生效/到期时间
└── 远程审批链与状态
```

本地 DSH 允许发起、自认领、拒绝和准备移交材料；远程控制平面负责权威身份、策略计算、审批和短期 capability 下发。

## 6. 实现状态语法

所有原型页面和组件必须使用统一状态标识：

| 标识 | 含义 | UI 规则 |
|---|---|---|
| `已实现` | 仓库中存在并有可重复验证 | 绿色；提供真实入口 |
| `已接入` | 外部系统真实连接且数据可验证 | 绿色；显示来源和同步时间 |
| `局部实现` | 只有部分链路可用 | 蓝色；明确可用/不可用边界 |
| `模拟数据` | UI 使用固定样例 | 琥珀色横幅；禁止出现“已连接” |
| `概念探索` | 尚无后端、schema 或执行能力 | 紫色虚线/水印；按钮不伪装成功 |

| 能力 | 状态 |
|---|---|
| Revolution Electron 产品壳与品牌 | 已实现 |
| DSH session/agent/tool 基础能力 | 已实现（上游能力） |
| Workflow Studio 原生事件只读投影 | 已实现，7 项测试通过 |
| 子会话打开、候选文件预览、manifest 导出 | 已实现 |
| 项目/Scrum/工作包看板 | 概念探索 |
| GitHub/Coding 连接器与 PR/CI 聚合 | 概念探索 |
| 远程控制平面、责任变更、业务审批 | 概念探索 |
| 资源中心、租约和 token 资源池 | 概念探索 |
| 插件市场与签名供应链 | 概念探索 |

## 7. Figma 首轮新增画面

在现有 `01 · 产品设计` 页面中，沿用 Noto Sans SC、1600 × 1000、8px 间距体系及现有 Button/Status/Navigation/TaskCard 组件，新增以下 Frame：

1. `V3 · 01 个人需求与工作包`：聚合飞书、会议、GitHub/Coding 与远程下发；展示“本地草稿 → 共享注册”的边界。
2. `V3 · 02 开发看板与仓库`：看板、原生仓库摘要、DSH 执行、PR/CI 证据同屏；仓库高级操作提供外部深链。
3. `V3 · 03 资源中心`：资源分类、组合设备拓扑、板卡/HIL 租约、token 配额和权限状态。
4. `V3 · 04 责任变更与权限审批`：本地发起、权限 diff、远程审批链、授权生效/回收。
5. `V3 · 05 工具与插件`：已安装、团队目录、市场、开发模式与权限详情。

其中 `V3 · 02` 的 Workflow Studio 区域标记为“已实现能力整合”；其他新业务区域统一标记为“概念探索 / 模拟数据”，直到真实 adapter、事件 schema 和控制平面完成。

## 8. 首版交付顺序

1. 先画 `V3 · 02 开发看板与仓库`，验证最核心的个人开发闭环。
2. 再画 `V3 · 04 责任变更与权限审批`，验证本地意图与远程权威的边界。
3. 再画 `V3 · 03 资源中心`，确定组合资源与 token 配额是否能共用信息结构。
4. 最后画 `V3 · 05 工具与插件` 和 `V3 · 01 个人需求与工作包`。

每个 Frame 必须保留一块“事实边界”说明：哪些区域来自现有实现、哪些来自外部权威源、哪些仍是探索性 UI。
