# Revolution 知识库与消息机器人实施方案

更新时间：2026-10-24。本文记录并列知识库的实现和消息机器人后续工作。个人飞书权限尚未确认；尚未创建飞书远端文档或机器人。

## 1. 目标与试验范围

让每次 Revolution 开发沉淀成可检索、可引用、可复用的知识，再把问答、任务发起和执行结果接入消息入口。

第一阶段有三个**并列且内容完整相同**的落点：iCloud Drive 中的 Obsidian 库；**自己注册的个人飞书账号**中的普通云文档目录；同一个**个人飞书账号**中的知识库（Wiki）空间。GitHub 仓库存储同一批 Markdown 原文、清单和可移植导出工具。公司提供的飞书个人工作账号是另一个身份；公司账号及公司 DSH 平台是后续迁移目标，不参与个人账号试验，也不把公司资料复制到个人库。

## 2. 内容归属和信息架构

| 落点 | 同一批内容的载体 | 编辑与同步 |
| --- | --- | --- | --- |
| Obsidian / iCloud | 全部 Revolution 知识文章 | Markdown 编辑后可拉回 GitHub 工作树 |
| 个人飞书普通文档 | 全部 Revolution 知识文章 | 文本块编辑后可拉回 GitHub 工作树 |
| 个人飞书 Wiki | 全部 Revolution 知识文章 | 文本块编辑后可拉回 GitHub 工作树 |
| GitHub 个人仓库 | 同一批 Markdown 原文和稳定 ID 清单 | 克隆后可在公司电脑选择合规内容复用 |

每篇内容有稳定 ID，四处都应有完整副本；不按“草稿／协作／稳定版”把文章分配到不同平台。工具记录各副本的上次同步哈希与链接；可从任一目标拉回修改，再推送到另外两处。若 GitHub 工作树和目标副本都发生更改，同步报冲突，由人合并，不强制覆盖。飞书富文本块、评论和附件目前不参与 Markdown 往返，遇到这类修改会停止同步。

建议统一六个一级主题：`00-入口`、`10-产品与需求`、`20-架构与接口`、`30-开发与实验`、`40-运行与排障`、`50-发布与复盘`。现有 `docs/knowledge/` 的 CI/CD、Agent/DSH、Jev、Figma 和验收记录可作为首批候选，但逐篇确认可发布范围，不直接批量复制。

新增文章可采用以下元数据模板；现有 5 篇文章已通过 `knowledge/catalog.json` 分配稳定 ID：

```yaml
---
id: rev-kb-0001
title: DSH 升级验收
topic: 40-运行与排障
status: reviewed
visibility: shareable
owner: alan
updated: 2026-10-24
source_refs: []
reviewed_at:
---
```

正文尽量回答五个问题：适用场景、结论、可执行步骤、证据或来源、失效条件。避免只存聊天摘要；代码版本、DSH 版本和测试命令也要写清。飞书文档 ID 与令牌不写入仓库中的 frontmatter；个人飞书授权令牌只由进程环境提供。

## 3. 发布与检索流程

命令、环境变量和冲突处理见 [并列知识库使用说明](../knowledge/README.md)。

1. **采集**：从 issue、PR、Workflow 导出清单和故障处理中写出 Markdown；先确认是可以进入个人 GitHub 的个人知识。
2. **登记**：把文章加入 `knowledge/catalog.json`，运行 `npm run kb -- check`；稳定 ID 用于匹配三处副本。
3. **同步**：`sync-obsidian`、`sync-docs`、`sync-wiki` 或 `sync-all` 写入相同文章集合。首次同步 iCloud Obsidian 的 5 篇已经完成；个人飞书待授权后验收。
4. **反向编辑**：从某一处改文后运行对应的 `pull-*`；审阅 Git 差异，再同步另外两处。遇到并发修改先手工合并。
5. **复用**：将 Markdown 和清单提交到正确的个人 GitHub 仓库。公司电脑克隆后，只把获准使用的模板、流程和个人原创知识导入公司 DSH 知识库。公司内容和凭据留在公司环境。

首轮已有 5 篇同内容文章；下一批可扩展到 15–20 篇。普通文档与 Wiki 的比较指标应是同一问题在两处的可检索性、链接稳定性、编辑冲突率和维护耗时；比较结果不会改变三处均保存完整知识的原则。

### iCloud 与飞书接入顺序

- 在 iCloud Drive 的 `Obsidian/<vault-name>` 下创建库，并让常用设备保持本地下载；iCloud 同步不能替代定期备份。[Obsidian 官方同步指南](https://obsidian.md/help/Getting%20started/Sync%20your%20notes%20across%20devices)
- 飞书普通文档与 Wiki 连接器已实现创建、更新、读回与冲突检查；个人账号创建应用、授予文档和 Wiki 权限仍待确认，真实写入尚未验收。[飞书云文档集成说明](https://open.feishu.cn/solutions/detail/docs?lang=zh-CN)、[飞书开放平台更新记录](https://open.feishu.cn/changelog)
- 自动化只保存文档元数据与授权引用；凭据放用户设备安全存储或受保护的服务端密钥库，不写入仓库、Obsidian frontmatter 或日志。

## 4. 面向所有 Revolution 用户的机器人架构

通用入站事件、账号绑定、授权和去重接口已实现在 [`integrations/bot/`](../integrations/bot/README.md)，并有无凭据测试。它尚未连接真实飞书/微信回调或 DSH 任务队列。

消息入口与知识来源作为两个独立适配器，核心任务仍由该用户自己的 Revolution/DSH 会话执行：

```text
飞书应用机器人 ─┐
               ├─> 事件网关 → 身份映射/授权 → 用户工作空间 → DSH 会话/任务
微信官方入口 ───┘                                      │
                         回复队列 ← 脱敏结果/原文链接 ←┘
```

每个 Revolution 用户拥有自己的连接配置、知识库授权、会话和数据空间。消息必须绑定到正确的 `revolution_user_id + connector_account_id + channel_chat_id`；群聊默认只在明确 @ 机器人或触发指令时处理。用户可查看和撤销连接，删除连接后停止收发并清除令牌。网关校验平台签名或使用官方长连接，按事件 ID 去重、排队并快速确认，再异步运行任务；高风险文件写入、发布、跨账号转发仍走 Revolution 审批。机器人回复包括任务状态、可追溯来源和继续操作链接，避免在群里直接吐出完整私有文档。

### 飞书

双向对话用**应用机器人**，订阅接收消息事件并调用回复/发送消息 API；单向群通知可选自定义 Webhook 机器人，但它不能承担问答入口。[飞书机器人概览](https://open.feishu.cn/document/client-docs/bot-v3/bot-overview)、[自定义机器人限制](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)

首轮在个人飞书可用的开发/测试环境验证：私聊问答、@ 触发、引用个人普通文档和 Wiki、任务状态回传。若个人账号不具备创建企业自建应用或 Wiki API 权限，保持手工文档试验，并在具备权限的测试租户验证应用机器人。飞书长连接方式适合本地开发，但官方说明它只支持企业自建应用；面向跨租户所有用户时，需要可获授权的应用发行方式，或允许每个租户接入自己的应用，不能把个人应用 ID 当成全体用户凭据。[飞书长连接事件文档](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-)

### 微信

“微信机器人”先按实际入口选官方能力：公众号或微信客服用于面向微信用户的服务消息；企业微信自建应用面向组织内员工。个人微信号的任意好友/群聊自动收发，不应作为全用户产品的默认接入承诺。需要单独核定所选账号类型、认证、消息窗口、回调和可用 API 后再实现连接器。第一期将微信通道做成独立可选适配器，并用模拟事件完成端到端联调；拿到正式账号权限后接入真实回调。

### 多用户上线门槛

- 用户可自行绑定/解绑飞书与所选微信官方入口；一个人的连接不会访问另一个人的消息或知识库。
- 入站事件鉴权、重放防护、去重、限流、失败重试和审计记录通过测试；同一消息不会重复创建 DSH 任务。
- 本地 Revolution 离线时，网关保留受限时长的待处理任务并提示用户；不把本机 `127.0.0.1` 服务暴露到公网。
- 公司租户要另行获得管理员授权，重新评估数据驻留和权限。个人飞书试验结果只迁移模板与代码，不自动迁移内容。

## 5. 建议实施顺序

| 阶段 | 交付物 | 验收标准 |
| --- | --- | --- |
| A：知识整理 | GitHub Markdown 清单与 Obsidian 同内容副本 | 5 篇文章已登记并同步到 iCloud Obsidian |
| B：飞书双形态试验 | 同一批文章进入个人账号普通文档目录与 Wiki 空间 | 个人账号权限确认后，真实 API 读回与冲突验收 |
| C：Revolution 检索 | 本地索引、来源引用、权限过滤 | 结果可追溯；撤权后不再显示受限内容 |
| D：飞书机器人 | 单用户闭环，再扩展租户授权与多用户隔离 | 消息去重、任务状态、撤销连接验证通过 |
| E：微信连接器 | 确定官方账号类型后实现收发 | 官方回调和平台限制下完成真实账号验收 |
| F：公司试点 | 管理员批准后在公司账号建立普通文档试点 | 内容权限和数据归属由公司确认 |

目前需由账号持有人提供的实施信息：个人飞书是否可创建应用与 Wiki 空间、微信希望采用哪类官方账号入口、预期的用户部署方式（纯本地或托管网关）。这些信息不影响先完成 A 阶段和 B 阶段的手工试验。
